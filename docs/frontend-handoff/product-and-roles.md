# Продукт, роли и бизнес-правила

## Назначение

«Кураторская» поддерживает основной процесс: группа → ученица → индивидуальная стратегия → текущие
задачи → домашнее задание → проверка → прогресс. Встречи и согласования с Аней сохраняют отдельную
историю и не подменяют этот процесс.

## Люди и ответственность

- **Аня** — product owner и владелец CRM. В серверной модели это `role=admin`, `is_owner=true`, а
  не отдельная роль и не захардкоженный login
- **Софья** — frontend developer и куратор. Права определяются назначениями групп в БД
- **Елисей** — другой куратор с теми же правилами обычного admin
- **Ученицы** — пользователи с ролью `student`, привязанные к одному `Student` profile
- **Юрий** — отвечает за production infrastructure и deployment; приложение не должно изменять
  его несвязанные сервисы

## Матрица ролей

| Возможность | Owner | Admin/куратор | Student |
|---|---|---|---|
| Читать группы и данные учениц | Все | Все | Только свои |
| Изменять группу/профиль | Все | Только назначенная группа | Нет |
| Создать группу | Да, назначается себе | Да, назначается себе | Нет |
| Переназначить группу | Да | Нет | Нет |
| Управлять кураторами | Да | Только публичный список | Нет |
| Управлять student account | Любой профиль | Только назначенная группа | Нет |
| Читать стратегию/встречи/ДЗ | Все | Все | Только свои |
| Изменять обучение | Все | Только назначенная группа | Только submit/resubmit собственного ДЗ |
| Legacy import/export | Да | Нет | Нет |

Client-side скрытие кнопок улучшает UX, но не является security boundary. Каждый запрос проверяется
backend по session, роли и цепочке фактических связей в БД.

## Инварианты и влияние на UI

1. Один curator ведёт много групп; у группы всегда ровно один активный admin. UI не отправляет
   `curator_id` при создании группы
2. Ученица принадлежит одной группе. Обычный profile PATCH не меняет `group_id`
3. Статус группы меняется вручную. Даты не завершают группу автоматически
4. Архивирование не удаляет историю и не отнимает student-read
5. У ученицы не более одной стратегии; разделы и задачи упорядочены
6. `period_text` — текст периода, не обязательный дедлайн; `due_at` отдельный и опциональный
7. `study_status`, `review_status` и `AnyaApproval.status` — три независимых состояния
8. Draft/issued ДЗ не завершают задачи; submitted ставит review `pending`, revision — `revision`,
   только accepted ставит задачу `done/accepted`
9. Пока review `pending|revision`, ручное изменение study status блокируется сервером
10. `HomeworkItem` — неизменяемый snapshot. Редактирование/архивирование задачи его не меняет
11. Встречи, task history и homework history сохраняются; физическое удаление не используется
12. Temporary password показывается только в ответе create/reset и затем недоступен

Frontend должен отображать `404` как недоступный/несуществующий объект, `403` как запрещённое
действие над доступным объектом, `409` как конфликт актуальности/состояния и `422` как ошибку ввода.

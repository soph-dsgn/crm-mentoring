# Стандарты качества и CI

## TDD workflow

Новая бизнес-логика и исправления дефектов по умолчанию проходят обязательный цикл:

1. **RED** — тест фиксирует согласованное требование и ожидаемо падает по правильной причине
2. **GREEN** — добавляется минимальная реализация, достаточная для прохождения теста
3. **REFACTOR** — код улучшается без изменения поведения, все тесты остаются зелёными

Для каждого исправленного дефекта нужен регрессионный тест. Корректные тесты нельзя удалять,
отключать или ослаблять только ради прохождения CI. Для инфраструктурных изменений допустим
test-after, если итог проверяется автоматизированным тестом или соответствующей командой.

## Последовательность локальных проверок

- Во время RED → GREEN → REFACTOR запускайте targeted tests, affected lint и focused validation для изменяемого пути
- После завершения функционального блока запускайте integration tests и регрессии затронутых модулей
- Перед Pull Request выполняйте полный backend pytest с branch coverage, Ruff, Alembic checks и релевантные frontend lint/build/workflow checks
- Перед финальной готовностью проведите Double QA: сначала проверку требований и бизнес-инвариантов, затем независимый повторный просмотр diff, ошибок, краевых случаев и пропущенных тестов
- Если менялись auth, RBAC, доступ к объектам, сессии, транзакции, конкурентные записи, миграции, audit или чувствительные данные, дополнительно проведите отдельный security review

Targeted-проверки ускоряют итерацию, но не заменяют полный набор обязательных gates перед Pull Request.

## Уровни тестирования backend

- **Unit tests** проверяют бизнес-правила, валидацию, переходы статусов и негативные сценарии в
  изоляции от HTTP и постоянной БД
- **Integration tests** проверяют репозитории, транзакции, ограничения SQLAlchemy и миграции на
  отдельной тестовой SQLite; локальная пользовательская БД не используется
- **API tests** через HTTPX проверяют HTTP-контракты, ошибки, аутентификацию, RBAC и доступ к
  конкретным объектам

Тестовые данные должны быть вымышленными и не должны содержать реальные данные учениц.

## Coverage policy

`pytest` измеряет строки и ветвления для всего пакета `backend/app`. Общий блокирующий порог —
75%. Бизнес-логику нельзя исключать из coverage без отдельного архитектурного обоснования.
Для будущих модулей auth и RBAC целевой ориентир — 90–95%, но отдельный блокирующий порог пока
не установлен.

## Обязательные CI-проверки

Workflow `.github/workflows/ci.yml` запускается для Pull Request в `main`, push в `main` и
вручную. Он использует минимальное разрешение `contents: read` и содержит две обязательные jobs:

- **Backend Quality**: Python 3.13, установка dev-зависимостей, Ruff lint, Ruff format check,
  pytest с branch coverage и порогом 75%, `alembic upgrade head`, `alembic current`,
  `alembic check`
- **Frontend Quality**: Node.js 24 LTS, `npm ci`, ESLint, TypeScript/Vite build и существующая
  сценарная регрессия

Обязательные шаги не используют `continue-on-error` и не пропускаются условно.

## Локальный запуск

Backend из каталога `backend/`:

```powershell
py -3.13 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
ruff check .
ruff format --check .
pytest
alembic upgrade head
alembic current
alembic check
```

Frontend из каталога `frontend/`:

```powershell
npm ci
npm run lint
npm run build
npm run verify:workflow
```

Также перед Pull Request выполните из корня `git diff --check`.

## Definition of Done

### Backend

- согласованные требования покрыты unit, integration или API-тестами подходящего уровня
- для новой бизнес-логики соблюдён RED → GREEN → REFACTOR, для исправленного бага добавлен
  регрессионный тест
- тестовая БД изолирована от локальных пользовательских данных
- Ruff, pytest, coverage не ниже 75% и Alembic checks проходят
- изменения контрактов и архитектурные компромиссы отражены в документации

### Frontend

- бизнес-правила и действующий пользовательский сценарий не нарушены
- ESLint, TypeScript/Vite build и `frontend/scripts/verify-workflow.mjs` проходят
- новый тестовый фреймворк не добавлен без отдельного обоснования
- если затронут интерфейс, выполнена релевантная desktop/mobile-проверка либо явно указано,
  почему она не выполнялась

Работа не считается завершённой, если обязательная проверка не была фактически запущена или
её результат скрыт. Незапущенные проверки и их причины перечисляются в отчёте явно.

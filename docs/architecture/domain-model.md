# Доменная модель

Здесь разделены факты текущего фронтенда и предлагаемая серверная модель. Последняя требует согласования до создания Alembic migration.

## Обнаруженная модель AppData v3

| Сущность | Фактические связи и важные поля |
|---|---|
| `Group` | `id`, имя, плановые и фактическая даты, ручной `status`, предыдущий статус архива, заметки |
| `Student` | ровно один `groupId`; профиль, контакты, точка А/Б, заметки, этап и время обновления стратегии |
| `StrategySection` | принадлежит ученице, имеет исходное название и порядок |
| `StrategyTask` | принадлежит ученице и разделу; содержит текст, период, материалы, дедлайн, порядок, историю, статусы выполнения, проверки и согласования |
| `Meeting` | принадлежит ученице; дата, заголовок, итог встречи |
| `Homework` | принадлежит ученице; содержит снимки выбранных задач и ссылки на их ID, текст, сроки, ссылку на работу, комментарий и soft-delete timestamp |
| `KnowledgeRecord` | отдельная IndexedDB-модель для промптов/учебника с source hash, признаками пользовательской правки, удаления и избранного |

Фронтенд хранит одновременно `status: backlog/progress/done` и более точный `studyStatus`. `taskColumn` вычисляет представление с учётом статуса проверки. В серверной модели рекомендуется оставить `study_status` каноническим, а старый `status` вычислять только в адаптере миграции/ответе совместимости.

## Целевая серверная модель

```text
User(admin) ──1──* Group ──1──* StudentProfile ──0..1── User(student)
   │                               │
   │                               └──1 Strategy ──* StrategySection ──* StrategyTask
   └──* Session                                        │                    │
                                                      │                    └──* TaskHistory
                                                      │                    └──0..1 AnyaApproval
                                                      └──* Homework ──* HomeworkItem *──0..1 StrategyTask
                                                                       └──* Submission ──* FileAsset (позже)
```

### Идентичность и обучение

- `User`: логин, роль `admin|student`, хэш пароля, `must_change_password`, активность, `is_owner`. Флаг владельца не является третьей ролью.
- `StudentProfile`: профиль ученика, связанный с одним `User` и одной группой. Персональные поля из текущего `Student` переносятся без потери.
- `Group`: собственный ручной жизненный цикл `backlog|active|completed|archived`; обязательный `curator_id` указывает назначенного куратора. Один куратор может вести много групп, у группы один назначенный куратор. Создатель группы назначается автоматически. Плановые даты не меняют статус автоматически.
  Обязательный `group_id` фиксирует правило: один ученик состоит строго в одной группе, группа содержит много учеников. Завершение или архивирование группы не удаляет профиль и не отнимает доступ ученика к материалам.

### Стратегия

- `Strategy`: связывается непосредственно с `StudentProfile`; у ученика одна текущая стратегия, соответствующая его единственной группе.
- `StrategySection`: исходное название, `position`, source metadata. Разделы всегда последовательны, не Kanban.
- `StrategyTask`: принадлежит стратегии и разделу; канонический статус `not_started|in_progress|hold|done`; `period_text` не является дедлайном; `due_at` опционален.
- `TaskHistory`: неизменяемая история значимых переходов. Для аудита хранит actor и timestamp.
- `AnyaApproval`: отдельное состояние `to_send|sent|reviewing|revision|approved`, тип, комментарий, время передачи. Оно не меняет выполнение или проверку ДЗ и не создаёт копию задачи.

Текущий `owner: Не назначен|Софья|Аня` нельзя переносить как enum пользователей: уже требуется третий куратор. Рекомендуется nullable FK `assignee_user_id`, а специальное согласование с Аней хранить отдельно.

### Домашнее задание

- `Homework`: принадлежит стратегии, имеет `draft|issued|progress|submitted|revision|accepted`, текст, даты и soft delete.
- `HomeworkItem`: хранит FK на исходную задачу и неизменяемый снимок её заголовка, описания, URL, материалов и дедлайна на момент создания ДЗ. Удаление/редактирование задачи не переписывает снимок.
- `Submission`: зарезервировано для будущих сдач ссылками и файлами. На текущем этапе не реализуется.

Правила, подтверждённые кодом:

1. Создание, генерация текста и копирование ДЗ не завершают задачи.
2. При `submitted` связанные задачи получают review `pending` и остаются в работе.
3. При `revision` review становится `revision`, задача остаётся `in_progress`.
4. Только `accepted` переводит связанные задачи в `done` и повышает прогресс.
5. После выдачи черновый текст, заголовок и набор снимков нельзя переписывать текущей функцией patch.
6. Пока review `pending|revision`, ручная смена статуса выполнения блокируется.

### Файлы и встречи

`FileAsset` в будущем хранит только метаданные, owner, storage key, MIME, размер и checksum; бинарные данные не должны жить в основных таблицах. Для локальной разработки допустим filesystem adapter, для production — объектное хранилище после выбора инфраструктуры.

Существующие `Meeting` нельзя потерять. До появления отдельного модуля они могут принадлежать `students` как подресурс профиля. Материалы базы знаний также входят в миграционный инвентарь, но не смешиваются со стратегиями и файлами учеников.

## Инварианты БД и сервисов

- даты и статусы группы не каскадируют статус стратегии;
- `period_text` не участвует в расчёте просрочки;
- порядок разделов уникален внутри стратегии, порядок задач — внутри раздела;
- не более одной стратегии на ученика;
- объектные проверки доступа выполняются до чтения/изменения ресурса;
- исторические и принятые данные удаляются мягко либо архивируются;
- timestamps хранятся в UTC, календарные даты — типом `date` без timezone;
- внешние legacy ID сохраняются в таблице соответствий импорта, а не становятся бизнес-ключами.

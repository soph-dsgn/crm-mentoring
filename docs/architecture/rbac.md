# RBAC и объектный доступ

Роли строго две: `admin` и `student`. Дополнительные полномочия владельца задаются флагом/permission на admin-пользователе, а не третьей ролью. В текущей команде Аня — владелец, Софья и Елисей — кураторы с ролью `admin`; проверять полномочия по отображаемому имени нельзя.

## Матрица доступа

| Действие | Владелец (`admin`, global) | Назначенный куратор (`admin`) | Неназначенный куратор (`admin`) | `student` |
|---|---:|---:|---:|---:|
| Просматривать группы и связанных учеников | да | да | да | только свой профиль и группу |
| Создавать группу | да | да, становится назначенным | да, становится назначенным | нет |
| Менять/архивировать группу | да | да | нет | нет |
| Переназначать куратора группы | да | рекомендуется нет | нет | нет |
| Создавать/деактивировать аккаунт ученика | да | да, только для назначенной группы | нет | нет |
| Читать профиль/стратегию/ДЗ | да | да | да | только собственные |
| Менять профиль, стратегию, задачи, встречи | да | только в назначенной группе | нет | нет |
| Выдавать и проверять ДЗ | да | только в назначенной группе | нет | нет |
| Менять глобальное согласование с Аней | да | передавать/исправлять в назначенной группе | только читать | нет |
| Создавать/деактивировать кураторов, переносить группы | да | нет | нет | нет |
| Сбрасывать пароль | любой пользователь | ученица назначенной группы | нет | нет |
| Читать свои материалы после выпуска | применимо | применимо | применимо | да |

Обычный admin может видеть безопасный список кураторов, но не может создавать, деактивировать,
переназначать или повышать их до owner. Полномочия вычисляются только по данным БД, без привязки
к именам, логинам и фиксированным идентификаторам сотрудников.

## Правило объектной области

Маршрут проверяет аутентификацию и роль, но этого недостаточно. Сервис загружает объект вместе с его группой и применяет область:

- owner: любая группа;
- admin-read: любая группа;
- admin-write: только `group.curator_id == actor.id`;
- student: только `student_profile.user_id == actor.id`;
- завершённая или архивная группа не отнимает student-read.

Для вложенных объектов право наследуется по цепочке «стратегия → ученик → группа», а не от переданного клиентом `student_id`. Репозиторий должен принимать access scope либо возвращать объект уже ограниченным запросом. Ошибка для чужого объекта — `404`, чтобы не раскрывать его существование; `403` используется, когда объект доступен для чтения, но запрещено действие.

## Создание и изменение паролей

- аккаунт создаёт администратор;
- временный пароль генерируется криптографически стойко, показывается один раз и хранится только как Argon2id hash;
- `must_change_password=true` разрешает только вход, смену пароля, выход и чтение минимального профиля;
- после смены пароля все прежние сессии отзываются;
- сессии — случайные opaque tokens; в БД хранится hash, в браузере — `HttpOnly`, `Secure`, `SameSite=Lax` cookie;
- для cookie-auth нужны CSRF-защита изменяющих запросов, ограничение попыток входа и audit events. Redis для масштаба проекта не требуется: сессии и счётчики можно хранить в SQL.

Auth Core реализован на server-side sessions. Объектные permission-функции и FastAPI dependencies
централизованы в `app.modules.auth.authorization`: они загружают `Group` и `Student` из БД,
скрывают недоступные объекты через `404` и возвращают `403` для запрещённой записи в доступный
для чтения объект. User Management переиспользует эти проверки для student scope, назначения
групп, offboarding и защиты последнего owner.

## Инвариант владельца и административные транзакции

- если в системе появился активный owner, деактивация, снятие `is_owner`, изменение роли и удаление
  последнего активного owner запрещены;
- первый owner назначается только внутренним `bootstrap_first_owner`, публичного bootstrap endpoint нет;
- передача полномочий выполняется `transfer_ownership` только на активного admin;
- переназначение групп и деактивация бывшего куратора объединяются сервисом
  `reassign_groups_and_deactivate`, который использует savepoint и не выполняет `commit`;
- SQLite дополнительно защищает инвариант owner на уровне trigger, поэтому конкурентные записи не
  могут оставить базу без активного owner.
- User Management migration добавляет SQLite triggers для второго межтабличного инварианта:
  группа всегда ссылается на активного admin, а admin с назначенной группой нельзя деактивировать
  или перевести в другую роль. Upgrade останавливается до изменения схемы, если старые данные уже
  нарушают этот инвариант.

Миграция `20261026_0008` добавляет эквивалентные PostgreSQL triggers. Защита последнего owner
сериализуется advisory transaction lock, а назначения кураторов и создание учениц — блокировками
соответствующих строк. Сервисы по-прежнему выполняют проверки полномочий и версий в той же транзакции.

## User Management и audit

- создание curator всегда задаёт `role=admin`, `is_owner=false`, `is_active=true` и
  `must_change_password=true`;
- student-аккаунт создаётся только для существующего `Student`, не меняет группу и не создаёт
  новый профиль;
- reset-password сохраняет только Argon2id hash, включает обязательную смену пароля и отзывает
  все активные сессии;
- обычный куратор управляет student-аккаунтом только через назначенную ему группу; подмена ID
  возвращает `404`;
- offboarding переносит все группы, отзывает сессии, деактивирует куратора и пишет audit events
  в одной транзакции; каждое назначение обновляется условно по ожидаемому `curator_id`, поэтому
  устаревшее назначение возвращает `409`, а не перезаписывает более свежее изменение;
- `AuditEvent` сохраняет actor, необязательные target user/group, тип действия, timestamp и
  минимальные безопасные details. Пароли и токены в журнал не записываются;
- DB unique constraints защищают normalized login, а условное связывание `Student.user_id`
  исключает две успешные конкурентные привязки на SQLite.

SQLite и PostgreSQL 18 проверены автоматизированными тестами, включая конкурирующие назначения,
защиту последнего owner, optimistic concurrency и совместный lifecycle домашних заданий и задач.
PostgreSQL-тесты выполняются на `READ COMMITTED` с независимыми соединениями; при смене isolation
level или схемы блокировок их необходимо повторить.

## Применение к Groups & Students API

- owner читает и изменяет любые группы и профили;
- admin читает все группы и профили, но изменяет и создаёт учениц только в назначенных группах;
- student видит только собственную группу и профиль, включая после архивирования группы/профиля;
- список состава группы предназначен только для admin, чтобы не раскрывать ученице roster;
- чужой объект для student возвращает `404`; доступный admin объект при отсутствии write-scope —
  `403`;
- назначение куратора и связь профиля с аккаунтом не принимаются business PATCH/Create schemas;
- условные UPDATE повторно проверяют текущего куратора вместе с `version`, поэтому устаревший
  permission check не даёт записать данные после конкурентного переназначения.

## Применение к Strategies & Tasks API

- право вычисляется по серверной цепочке `StrategyTask → Strategy → Student → Group`;
- owner читает и изменяет любые стратегии, admin читает все и изменяет только назначенные группы;
- student читает только собственную стратегию, разделы, задачи, историю и согласование, но не
  выполняет mutations;
- архивный lifecycle группы не отнимает student-read;
- условные UPDATE задачи, раздела и согласования одновременно проверяют `expected_version` и
  актуальное назначение куратора; client-provided IDs не определяют access scope;
- `strategy_id`, `section_id`, archive/status fields и actor history не принимаются обычным PATCH.

## Применение к Meetings & Homeworks API

- право наследуется по цепочке `Meeting → Student → Group` и
  `Homework → Strategy → Student → Group`;
- admin читает все встречи и ДЗ, но изменяет только данные назначенных групп; owner имеет полный
  доступ; student читает только собственные ресурсы;
- student может только перевести собственное ДЗ в `progress|submitted`; выдача, возврат,
  принятие, архивирование и изменение встреч доступны admin в write-scope;
- student-ответ встречи скрывает внутренние заметки, а история ДЗ — staff actor ID;
- условные UPDATE одновременно проверяют `expected_version` и текущее назначение куратора;
  CSRF и same-origin обязательны для каждой mutation.

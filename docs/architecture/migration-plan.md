# План переноса localStorage и JSON

Перенос должен быть отдельным, повторяемым и обратимым процессом. Текущий фронтенд продолжает быть источником пользовательских правок до момента переключения; `frontend/public/strategies/strategy-seed.json` и PDF — источники исходных материалов, но не замена актуальному browser backup.

## Источники

1. Экспорт `crm-mentoring-v1` через существующее окно резервных копий — рабочие группы, профили, разделы, задачи, встречи и ДЗ.
2. Автоматические browser backups до импорта/обновления разделов — страховка и источник сверки.
3. `frontend/public/strategies/strategy-seed.json` и 19 PDF — исходный материал и стабильные source IDs.
4. Экспорт IndexedDB базы знаний — отдельный поток для промптов и учебника.

Доступ к localStorage другого браузера сервер получить не может. Экспорт выполняет пользователь на каждом рабочем профиле браузера; до переключения нужно подтвердить, где находится наиболее свежая копия.

## Этапы

### 1. Инвентаризация и заморозка формата

- получить JSON только через существующий export, не читать и не изменять пользовательский browser storage скриптами;
- записать размер, SHA-256, `version`, counts и время получения;
- сохранить зашифрованную резервную копию вне рабочей БД с ограниченным доступом;
- сравнить несколько копий и выбрать каноническую только после ручного подтверждения владельца.

### 2. Validate-only

- Pydantic-схема принимает версии 1–3 и повторяет документированную нормализацию, но не исправляет данные молча;
- проверить ID, ссылки, enum, даты, orphan records, дубли имён и ссылочную целостность;
- сформировать отчёт: create/match/conflict/skip и отдельный список персональных записей для ручной сверки;
- проверить контрольные количества seed (4/19/90/749), не считая их гарантией полноты пользовательского backup.

### 3. Преобразование

- `Group` → group с `legacy_id` mapping;
- каждый legacy `Student(groupId)` → user + student_profile с обязательным `group_id` + strategy;
- одинаковые имена в разных группах не считать одним учеником и не объединять автоматически;
- sections/tasks → соответствующая strategy с сохранением порядка, source file и history;
- старый `status` сохранить в raw import record, канонический `study_status` получить по тем же правилам, что `normalizeData`;
- approval переносить отдельно от homework review;
- HomeworkItem переносить как snapshot плюс FK к задаче; Meetings не терять;
- knowledge импортировать отдельным job с сохранением `sourceId`, hash и признаков пользовательской правки.

### 4. Транзакционный импорт

- перед импортом сделать backup SQLite/PostgreSQL;
- создать `import_run` с checksum источника и уникальным ключом идемпотентности;
- импортировать одну полную копию в транзакции; при ошибке откатить всё;
- повтор того же checksum не создаёт дубли;
- конфликты не перезаписывают серверные правки и требуют явного решения.

### 5. Приёмка и переключение

- сверить counts, выборочные профили, порядок разделов, task statuses, прогресс, ДЗ, встречи и согласования;
- проиграть основной сценарий «группа → ученица → стратегия → ДЗ → проверка → прогресс»;
- выполнить экспорт из сервера и проверить восстановление на отдельной БД;
- только после подписи владельца перевести React на API; localStorage оставить read-only fallback на оговорённый срок;
- хранить rollback backup и mapping legacy IDs до завершения периода наблюдения.

## Защита персональных данных

Не использовать реальный backup в тестах, CI, логах и Git. Для автотестов нужен синтетический набор без имён, Telegram и ссылок пользователей. Импорт-отчёты по умолчанию содержат IDs и counts, а не полные записи. Временные файлы удаляются после подтверждённого импорта согласно согласованной политике хранения.

## Критерии готовности мигратора

- dry-run ничего не записывает;
- повторный импорт идемпотентен;
- ни одна пользовательская правка не заменяется seed-значением без конфликта;
- все FK и snapshots проверены;
- экспорт и восстановление серверного backup протестированы;
- есть документированная процедура rollback.

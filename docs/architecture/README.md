# Архитектура бэкенда «кураторской»

Статус: проектирование foundation, 22 октября 2026 года. Реализован только технический каркас; описанные ниже доменные модели и API являются целевой схемой, а не работающей серверной функциональностью.

## Результат аудита существующего приложения

Фронтенд — одностраничное React 19 + TypeScript + Vite приложение без серверной части. Корневая точка состояния — `AppData` версии 3 из `src/types.ts`. Основные операции выполняются в `src/App.tsx`, а переходы статусов и нормализация старых форматов — в `src/data.ts`.

Фактическое хранение разделено на два механизма. Текущая связь `Student.groupId` соответствует уточнённому правилу: один ученик состоит строго в одной группе; один назначенный куратор может вести много групп.

- рабочие сущности (`groups`, `students`, `sections`, `tasks`, `meetings`, `homeworks`) целиком сериализуются в `localStorage` под ключом `crm-mentoring-v1`;
- промпты и учебник хранятся отдельно в IndexedDB `crm-mentoring-knowledge`, умеют импортировать DOCX/Markdown/HTML и экспортироваться в JSON.

При чтении `normalizeData` принимает версии 1–3, заполняет новые поля и восстанавливает безопасные значения по умолчанию. Перед обновлениями создаются локальные копии. Некорректный JSON сохраняется под recovery-ключом, после чего приложение открывается с пустыми данными. Полный JSON-бэкап можно скачать и восстановить с подтверждением полной замены.

`frontend/public/strategies` содержит 19 исходных PDF. `frontend/scripts/import-strategies.py` формирует стабильный seed: 4 группы, 19 профилей, 90 разделов и 749 задач. `mergeStrategies` удаляет только demo-записи, сопоставляет группы по стабильному ID либо имени и дате, профили — по ID либо имени внутри группы, не перезаписывает пользовательские правки и фиксирует конфликты. Два продолжения строк без заголовка сохранены в заметках профилей, а не потеряны.

`frontend/scripts/verify-workflow.mjs` проверяет повторяемый импорт, сохранность правок, преобразование legacy-данных, календарные даты, прогресс, цикл проверки ДЗ, независимый цикл согласования с Аней и серверный рендер ключевых экранов. Отдельный Python-скрипт сверяет полноту импорта материалов базы знаний. Формального unit-test framework во фронтенде пока нет.

## Архитектурный стиль

Выбран модульный монолит. Для команды и объёма 50–300 учеников он даёт транзакции между стратегиями и ДЗ без распределённой инфраструктуры, простой деплой и ясные границы для роста.

```text
HTTP / FastAPI
    ↓
API-схемы и зависимости доступа
    ↓
сервисы вариантов использования и объектные проверки прав
    ↓
репозитории / SQLAlchemy Unit of Work
    ↓
SQLite → PostgreSQL
```

Модули: `auth`, `users`, `groups`, `students`, `strategies`, `homeworks`, `files`. Общие `core` и `db` содержат только инфраструктуру. Модуль не должен изменять таблицы другого модуля напрямую: межмодульный сценарий координирует сервис приложения в одной транзакции.

Внутри каждого модуля по мере реализации появятся `api`, `schemas`, `service`, `repository` и `models`. Пустой шаблон этих файлов сейчас не создан: границы обозначены пакетами, а код будет добавляться вместе с первым реальным сценарием.

## Текущая структура

```text
backend/
  app/
    api/              # композиция HTTP-маршрутов и /health
    core/             # настройки окружения
    db/               # metadata, engine, session
    modules/          # границы доменных модулей
  migrations/         # Alembic; первая revision появится с моделями
  tests/              # изолированные backend-тесты
  pyproject.toml
docs/
  architecture/
```

Foundation использует синхронный SQLAlchemy. Для текущей нагрузки это проще и достаточно; FastAPI запускает обычные `def`-обработчики в thread pool. Имена ограничений заданы явно, URL БД приходит из окружения, SQLite-специфичный `check_same_thread` изолирован в фабрике engine, а Alembic включает batch-режим только для SQLite. Это оставляет переход на PostgreSQL конфигурационной и миграционной задачей, а не переписыванием слоёв.

## Границы текущего этапа

Работает `GET /health`, загрузка конфигурации, создание SQLAlchemy engine и Alembic environment. Авторизация, модели, CRUD, загрузка файлов, миграция реальных данных и интеграция с React отсутствуют намеренно. Фронтенд и его данные не изменены.

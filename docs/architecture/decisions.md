# Архитектурные решения и вопросы

## Принятые для foundation решения

### D-001 — Модульный монолит

Один FastAPI deployment и одна реляционная БД. Для 50–300 учеников микросервисы, брокер, Redis и фоновые очереди добавят эксплуатационный риск без подтверждённой пользы.

### D-002 — Синхронный SQLAlchemy 2

Текущие сценарии преимущественно CRUD и короткие транзакции. Синхронная модель проще для команды и Alembic. Async можно рассмотреть только по результатам измерений, не заранее.

### D-003 — SQLite сейчас, PostgreSQL-ready границы

Локально используется SQLite; URL задаётся окружением, типы и ограничения должны быть переносимыми, Alembic — единственный способ менять схему. PostgreSQL-драйвер не добавлен до выбора deployment platform.

### D-004 — Доменные таблицы добавляются согласованными вертикальными срезами

Пустая baseline migration и десятки предварительных моделей создали бы ложное ощущение
утверждённой схемы. Первая revision `20261022_0001` добавляет только согласованный срез
users/groups/students; стратегии, ДЗ и остальные сущности получат отдельные миграции.

### D-005 — Консервативные диапазоны зависимостей

`pyproject.toml` задаёт минимальные версии с поддержкой Python 3.13 и верхнюю границу следующего major. Resolver подтвердил наличие полного набора Windows wheels для CPython 3.13. Перед production всё равно нужен lock-файл, собранный и протестированный самим Python 3.13; доступный для аудита встроенный runtime имеет версию 3.12 и используется только для дополнительного функционального прогона.

### D-006 — Один ученик в одной группе, один куратор у многих групп

`Student.group_id` обязателен: ученик состоит строго в одной группе. `Group.curator_id` обязателен:
у группы один назначенный куратор, при этом один куратор может вести много групп. Стратегия
принадлежит ученику напрямую. Это соответствует исправленному требованию и текущему
frontend-полю `Student.groupId`.

## Рекомендуемые решения, требующие согласования

### Q-002 — Полномочия обычного куратора над аккаунтами

Требование говорит, что аккаунты создают администраторы, но не уточняет, любой ли куратор может создавать и сбрасывать аккаунты. Рекомендация: назначенный куратор может создать ученика только в своей группе, а блокировка, смена роли и глобальный reset доступны владельцу.

### Q-003 — Переназначение куратора

Рекомендация: менять назначенного куратора группы может только владелец. Создатель назначается автоматически, а переназначение выполняется атомарно, чтобы группа не оставалась без ответственного.

### Q-004 — Восстановление доступа

Для первой модели выбран уникальный строковый `login`; формат логина ещё нужно ограничить на
уровне схем/API. Требуется выбрать канал безопасной передачи временного пароля и политику
восстановления без email. Telegram не следует автоматически считать каналом аутентификации.

### Q-005 — Сроки сессии и аудит

Рекомендация: server-side opaque session, ограниченный idle/absolute lifetime, отзыв всех сессий при reset и аудит входов/изменений прав. Конкретные сроки и retention audit log нужно утвердить.

### Q-006 — Удаление и хранение данных

Рекомендация: группы, профили учеников, стратегии, ДЗ и аккаунты с историей архивировать, а не удалять физически. Нужны утверждённые сроки хранения персональных данных, backup и файлов после окончания обучения.

### Q-007 — Принятые ДЗ и несколько попыток

Текущая модель хранит одну ссылку и один комментарий в Homework. Будущая сдача файлов требует решить: поддерживать ли несколько Submission attempts, можно ли сдавать после accepted и кто может заменить/удалить файл. Рекомендация — append-only attempts с отдельным решением по каждой проверке.

### Q-008 — Конкурентное редактирование

После перехода от одного localStorage к нескольким кураторам возможна тихая перезапись. Рекомендация: optimistic locking через version/`updated_at`, `409 Conflict` и явное повторное применение правки.

### Q-009 — База знаний

Промпты и учебник существуют в IndexedDB, но не входят в запрошенный список backend-модулей. Нужно решить, мигрировать ли их в первой серверной версии и кто может редактировать. До решения они остаются отдельным источником и не включаются в foundation.

## Риски

- одинаковые имена в разных группах нельзя автоматически считать одним учеником;
- текущая модель связывает задачи непосредственно с `studentId`; при введении сущности Strategy мигратор должен сохранить явное соответствие старых задач новой стратегии этого ученика;
- старые `status` и `studyStatus` могут расходиться; мигратор должен воспроизвести действующую функцию нормализации;
- browser backups могут различаться между устройствами и профилями;
- файлы и PDF содержат персональные данные, значит CI и developer fixtures должны быть строго синтетическими;
- SQLite пригоден для текущего масштаба при одном процессе записи, но shared/multi-instance deployment потребует PostgreSQL;
- без зафиксированной политики auth нельзя безопасно реализовать temporary-password flow.

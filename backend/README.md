# Backend «Кураторской»

Модульный монолит на FastAPI и SQLAlchemy. Реализованы конфигурация приложения, подключение БД,
Alembic, доменные модели `User`, `Group`, `Student`, server-side Authentication Core, RBAC,
административный backend-модуль управления аккаунтами и REST API групп и профилей учениц.
Также реализованы серверные модули стратегий, задач, встреч, домашних заданий, истории и
согласований с Аней. React-интеграция и импорт frontend-данных в этот этап не входят.

Первая миграция создаёт пользователей, группы и профили учеников. Роли ограничены значениями
`admin|student`; полномочия владельца задаются отдельным флагом `is_owner`. Составные внешние
ключи не позволяют назначить student-пользователя куратором или связать admin-пользователя с
профилем ученика. Связанные пользователи и группы защищены `ON DELETE RESTRICT`; для завершения
жизненного цикла предусмотрены деактивация пользователя, архивный статус группы и архивирование
профиля ученика.

## Управление пользователями

Административные маршруты находятся под `/api/v1/admin`. Owner может создавать и деактивировать
кураторов, передавать полномочия owner, переназначать группы, выполнять атомарный offboarding и
сбрасывать пароли. Назначенный куратор может создавать, читать, деактивировать и сбрасывать пароль
аккаунта ученицы только в собственной группе. Ученица не имеет доступа к административным
маршрутам.

Временный пароль генерируется криптографически стойко, возвращается только ответом успешной
операции создания или reset-password и в БД хранится исключительно как Argon2id hash. После reset
все сессии пользователя отзываются, а `must_change_password=true` блокирует бизнес-операции до
смены пароля. Изменяющие запросы требуют действующую cookie-сессию, CSRF token и same-origin check.

`AuditEvent` хранит административные действия без паролей, session/CSRF tokens и иных секретов.
Audit event и бизнес-изменение фиксируются одной транзакцией. Деактивация сохраняет `User`,
`Student`, учебную историю и стабильные идентификаторы; физическое удаление audit history
ограничено внешними ключами `ON DELETE RESTRICT`.

SQLite triggers не позволяют назначить группе inactive admin и не позволяют деактивировать или
сменить роль куратора, пока за ним закреплена группа. Это закрывает гонку между переназначением и
деактивацией на уровне БД, а не только предварительными SELECT в сервисе.

## Группы и профили учениц

Маршруты `/api/v1/groups` и `/api/v1/students` реализуют создание, чтение, частичное изменение и
архивирование без физического удаления. Создатель группы всегда становится её куратором; назначение
нельзя передать через payload. Профиль ученицы создаётся только внутри существующей неархивной
группы и не получает `User`-аккаунт автоматически.

Изменения и lifecycle-команды требуют `expected_version`. Условный SQL `UPDATE` увеличивает
`version`; устаревшая версия или изменившееся назначение возвращает `409` и не перезаписывает
актуальные данные. Ответ archive/restore содержит обновлённый ресурс и новую версию. События
`group_*` и `student_*` записываются в `AuditEvent` той же транзакцией без текстов личных заметок.
Список состава группы доступен только admin; student получает собственный профиль и сокращённое
представление собственной группы без внутренних идентификаторов куратора.

## Стратегии и задачи

У ученицы может быть одна стратегия. Последовательные разделы и задачи имеют уникальные позиции,
optimistic version и атомарный reorder. `study_status` — канонический статус выполнения;
`period_text` не считается дедлайном. Редактирование, смена статуса, архивирование и восстановление
задачи добавляют append-only `TaskHistory`. Архивирование не удаляет задачу и не разрывает будущие
ссылки снимков домашних заданий.

`AnyaApproval` связан с исходной задачей один-к-одному и имеет отдельный lifecycle
`to_send → sent → reviewing → revision|approved`, включая повторную передачу и отзыв в `to_send`.
Он не меняет `study_status`. Все mutations требуют действующую business-сессию, CSRF и
same-origin, проверяют текущее назначение куратора внутри условного SQL и записывают безопасный
`AuditEvent` в той же транзакции.

## Встречи и домашние задания

Встречи принадлежат профилю ученицы, поддерживают cursor pagination, optimistic concurrency и
архивирование без удаления. Student читает только свои встречи и не получает внутренние заметки
куратора.

Домашнее задание принадлежит стратегии и хранит неизменяемые снимки выбранных задач. Выдача не
завершает задачи; отправка переводит их проверку в `pending`, возврат — в `revision`, и только
принятие переводит выполнение в `done`. Пока проверка ожидается или идёт доработка, ручная смена
`study_status` запрещена. Переходы, версии задач, append-only история и audit events фиксируются
одной транзакцией. Одна задача не может одновременно проверяться в двух домашних заданиях, а ДЗ
с активным review нельзя архивировать. Изменяющие маршруты повторно проверяют актуального куратора
в условном SQL.

## Требования

- Python 3.13+
- SQLite 3 (входит в стандартную поставку CPython) для локальной разработки
- PostgreSQL 18 для production

Заявленная совместимость основных зависимостей с Python 3.13 проверена по метаданным PyPI и отдельным разрешением бинарных пакетов для CPython 3.13 на Windows.

## Локальный запуск

Все команды выполняются из каталога `backend`.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
Copy-Item .env.example .env
alembic upgrade head
alembic check
uvicorn app.main:app --reload
```

Для bash/zsh активация окружения выполняется командой `source .venv/bin/activate`, а файл окружения можно создать через `cp .env.example .env`.

После запуска:

- health check: `http://127.0.0.1:8000/health`
- OpenAPI: `http://127.0.0.1:8000/docs`

## PostgreSQL 18

Приложение использует Psycopg 3 и тот же SQLAlchemy/Alembic stack. Создайте пустую базу и
отдельного пользователя с правами на её schema, затем задайте URL только через окружение:

```text
KURATORSKAYA_DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DATABASE?sslmode=require
KURATORSKAYA_DATABASE_POOL_SIZE=3
KURATORSKAYA_DATABASE_MAX_OVERFLOW=1
KURATORSKAYA_DATABASE_POOL_TIMEOUT_SECONDS=30
```

TLS-параметры зависят от сервера; production URL не должен отключать проверку TLS. После создания
пустой базы выполните `alembic upgrade head`, `alembic current` и `alembic check`. Миграция
`20261026_0008` устанавливает PostgreSQL triggers для active owner/curator, запрета создания
ученицы в архивной группе, cross-strategy HomeworkItem и неизменяемой истории.

Локальный integration test требует отдельную disposable PostgreSQL 18 базу:

```powershell
$env:KURATORSKAYA_TEST_POSTGRES_URL='postgresql+psycopg://USER:PASSWORD@127.0.0.1:5432/crm_test'
pytest tests/test_postgresql.py --no-cov
```

Имя disposable-базы должно оканчиваться на `_test`. Тест очищает schema `public`; не указывайте
рабочую или общую базу. Покрытие измеряется полным `pytest`. SQLite остаётся вариантом по умолчанию
и продолжает использовать собственные triggers и `PRAGMA foreign_keys=ON`.

## Проверки

```powershell
ruff check .
ruff format --check .
pytest
alembic current
alembic check
```

SQLite-файл по умолчанию создаётся как `backend/kuratorskaya.db` и игнорируется Git. PostgreSQL
проверяется отдельными migration/integrity/concurrency tests на реальном PostgreSQL 18. Проверенные
гарантии относятся к стандартному уровню изоляции `READ COMMITTED`; приложение упорядочивает
конкурирующие изменения optimistic versions, conditional updates и database triggers.
